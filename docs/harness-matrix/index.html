Status per harness

Each harness carries exactly one of four status words (owner decision 2026-10-17; Beta added 2026-10-18); the table below it keeps the per-plan facts.

  • Completed: rewrite observed honored on a real child, usage and child end recorded, plugin and session policy.
  • Functional: the hook emits the rewrite on a real spawn and passes the shared conformance suite; observation is partial (honored is inferred or unconfirmed, no child usage).
  • Beta: first-class integration under active development — adapter, route wire and shared conformance in the repository and green; the harness-side plugin and the first live observation are still ahead, so no live spawn is observed yet and there is no production claim (owner decision 2026-10-18).
  • Experimental (proof of concept): policy mode or one observed child on one build; shipped, but no production claim.

cmd/downshift/conformance_test.go drives the same 8 routing scenarios against every registered hook, so each harness below, whatever its status, computes every feature (layering rule); the status says how much has been verified on the real harness, not how much code it runs.

Only applied rewrites (outcome rewrite_emitted, no guardrail correction) count; allow, blocked and held events never do.

Decision linkage (current model and post-spawn cost)

Observed on claude-code 2026-10-12: the PreToolUse payload carries tool_use_id and transcript_path but no session model.

  • Current model. A Task call without model (agent type empty, general-purpose, claude, and the built-in Explore and Plan) runs on the session model. The adapter reads it from the last assistant message in the tail of transcript_path (1 MiB, model id only). Any other type is decided by its definition (2026-10-19): a built-in that runs on its own model (statusline-setup on Sonnet, claude-code-guide on Haiku) and an agent file whose model: names one are a known baseline that routing leaves alone (AGENT_PINS_MODEL); an agent file with no model: or inherit (project .claude/agents, user agents, or an installed plugin's agents, found through installed_plugins.json for a plugin:agent type) inherits like general-purpose. A type with no definition found stays unknown. Explore also stays unknown when the session model is Fable: Claude Code may run it on Opus (subscription, Console, gateway) or keep it on the main model (cloud providers), and a hook cannot tell which. Until 2026-10-15 Explore and Plan were left out, so every spawn of those types was held as HELD_UNCONFIDENT_UNKNOWN_MID and never routed.
  • Claude Code: parallel Agent calls in the first assistant message. The hook gets the session model from the last assistant message in the transcript, and Claude Code only writes a message to the transcript when it has finished streaming. When one message carries several Agent calls and no earlier assistant message exists (a headless run whose first action is to delegate), the hooks of all but the last call see an empty transcript. Measured in 3 runs of 5 parallel Agent calls: 4 of 5 spawns per run had no baseline and were held (HELD_UNCONFIDENT_UNKNOWN_MID). The 400 ms wait added for the write race does not help, because the message closes only after all its tool-use blocks have streamed, and SessionStart does not carry the model in claude -p either (checked 2026-10-15). Now, for an agent type that inherits the session model, when the transcript has no model the adapter falls back to the model the session is configured to use: ANTHROPIC_MODEL, then model in <cwd>/.claude/settings.local.json, <cwd>/.claude/settings.json and the user settings.json (CLAUDE_CONFIG_DIR honoured), first one that sets it. A full id passes through, opusplan is Opus under permission_mode plan and Sonnet otherwise, sonnet, opus, haiku and fable map to the catalog's model of that family, and default or anything unrecognised stays unknown. The decision carries BASELINE_FROM_SETTINGS. The result is an inference: the --model flag and a mid-session /model are not visible to a hook, so a session started with --model or switched with /model can be routed against the wrong baseline. To keep that guess from turning into a hidden upshift, a downshift on this baseline is written only to the small tier; a downshift to the mid tier is held. A model found in the transcript always wins, Explore under a Fable setting stays unknown, and agent types that do not inherit get no fallback. The native route remains the agent.spawn mod event, which hands over parentModel.
  • Baseline still unknown on Antigravity; Cursor inherit uses the parent when present. A spawn with an explicit model is known. Antigravity's inherit has no parent model in the payload. Cursor sends no transcript path (58 of 144 captured Task payloads, 2026-10-09/10). When a Cursor call has no tool_input.model or it is inherit, the parent's model_id (then payload model) is the baseline, and a downshift on it is written only to the small tier: a child can run on Composer or a fast variant, so a mid target could be an upshift. Without model_id, inherit logs as unknown.
  • Upshift ranking, all harnesses. An upshift ranks the session ids by catalog tier, not list position, and never goes below the current model's tier. A confident upshift lands on the least model at the needed tier; a guessed baseline (Claude Code settings, Cursor parent model_id) or explicit_upshift keeps the strongest tier. Codex, Antigravity and KiroCrew never guess a baseline, so they always take the needed-tier pick. The rule and its fallback are in session-models.md.
  • Cost linkage. Every decision records tool_use_hash. PostToolUse repeats the id, so resolved, child_ended and, through the agent id, usage attach to the exact decision even with parallel spawns, including held and allow decisions (no rewrite_honored claim for those), and control-group and no-route decisions (outcome: baseline): before 2026-10-19 the linker treated baseline as a cost record and skipped it, so no control spawn ever had an end record. Lines written before this field fall back to the session heuristic.
  • One spawn, two harnesses (all harnesses). Cursor runs the Claude Code hooks in ~/.claude/settings.json when its third-party configs are on (Cursor docs), so one Cursor spawn reaches both the cursor hook and the claude-code hook. Each harness declares PayloadMarkers (top-level keys only it sends; Cursor: cursor_version, conversation_id, generation_id, workspace_roots), and the shared hook, honor, usage and end runners leave a payload carrying another harness's marker to that harness's own hook: allowed unchanged, nothing recorded, one stderr line. Before 2026-10-19 the copy was routed and logged as a claude-code decision with Cursor's inherit and lowercase agent types: all 79 claude-code decisions labelled agent_type: custom in the operator's 30-day log were such copies (each within 3 s of a cursor decision; all 33 with a tool-call id shared it). Not verified on a live Cursor build: that the copy carries at least one marker. It is the native Cursor input, and the logged copies match it.
  • Custom agent types on Claude Code. A real custom type (project or user .claude/agents/<name>.md, or a plugin agent plugin:name) still logs an unknown baseline unless the call names a model: the payload carries only the type name, and the model its definition pins (or inherit) is in a file the hook does not read. Reading it is option 2 of subagent-type-signal.md, held back until it is measured. Built-in pinned types (claude-code-guide, statusline-setup) ship no definition on disk, so they stay unknown too.
  • Other harnesses. cursor and codex expose tool_use_id on decisions (documented in their hook payloads). Their end hooks (see "Child end" below) join on it when the end payload repeats the id.
  • codex current model. A spawn_agent call without model runs on the parent's current model: 22 of 24 such spawns in the operator's rollouts (2026-10-12; the other mismatches were Downshift's own rewrites). The adapter reads the last turn_context.payload.model from the tail of transcript_path. gpt-6.1-sol is registered for identity and tier and has list prices since #190 (2026-10-19), so cost telemetry can price it once a token source exists (Codex has none today). gpt-reserve is not in the catalog yet, so they still log as unknown with requested_model_raw set.
  • antigravity current model. Subagents[].Model arrives in the payload (2026-10-09 run asked for pro) but was never exposed to telemetry; it is now, for the subagent whose decision is recorded (the last with a prompt). The documented top-level modelName is not read until a real payload confirms it.
  • cursor current model. In 144 captured Task payloads (2026-10-09/10) the top-level model was always empty; the subagent model was a real id, inherit (28) or absent (30). With model_id on the payload, inherit is resolved like a missing tool_input.model and logged as that parent id; without model_id it logs as unknown.
  • Unrecognised models (all harnesses). When the requested model is non-empty but not in the catalog, the shared runner records it in requested_model_raw if it looks like a model id (64 chars, [A-Za-z0-9._:/-]), else invalid.

Child end (N5, 2026-10-13)

One shared recorder (internal/childend) writes resolved, child_ended and usage for any harness from a hookport.ChildEnd. An adapter only parses its payload (ParseChildEnd); the CLI entry is downshift end <harness>, and setup wires it from HarnessCapabilities.ChildEndEvent. downshift report and downshift doctor print, per harness, whether completion is measurable (an end event is declared and at least one end record has been seen; a launch is not an end). Claude Code keeps claude-code-post-tool-use and claude-code-subagent-stop as aliases of the same runner.

harness ChildEndEvent UsageSource status
claude-code SubagentStop (launch and failure also on PostToolUse / PostToolUseFailure) transcript (agent_transcript_path) verified 2026-10-06 (launch payload, SubagentStop transcript); failure payload still GAP-CHILD-FAILURE
codex PostToolUse for spawn_agent none (UsageSource: none): end and status are recorded, cost is not. A parser for the rollout token_count exists but stays off until a real payload proves transcript_path is the child's rollout unverified: needs a real payload. tool_response.status / model are assumed names; the token_count usage shape is from the Codex rollout format, not from a captured hook. A spawn that reports no status is a launch: it records launched, reads no usage and does not make completion measurable. transcript_path is the parent rollout, so until a real payload shows a child-scoped rollout the tokens may be the parent thread's.
cursor subagentStop none (no usage field is read) unverified: needs a real payload. Linked only when the payload names the spawn tool call (tool_use_id / tool_call_id); Cursor sends no session id, so otherwise nothing is recorded. No model is read.
antigravity none none no documented subagent-end payload (PostToolUse exists; its result fields are not documented). Nothing recorded.
kirocrew none none PostToolUse tool_response not confirmed (see evidence/vendor-hook-docs-2026-10-11.md). Nothing recorded.
opencode child_done (observation envelope the plugin forwards) none (UsageSource: none): the child_done parser reads status and inline usage counts, but nothing is priced. unverified: needs a live run. The envelope shape comes from the phase-0 probes, not from a captured plugin forward. The honor reader reports a resolved model only from the arrival-ordered switch chain; a batch without it records nothing.

Where ChildEndEvent is empty, downshift end <harness> exits 0, records nothing and says so on stderr.

Child-end line (U2, 2026-10-13)

HarnessCapabilities.CanShowChildLine says whether the hook protocol can show one line when a subagent ends. Claude Code: true (systemMessage on PostToolUse and SubagentStop), pending a live check. cursor, codex, antigravity, kirocrew, opencode: false; the line is still computed by telemetry.ChildEndLine (by the shared recorder, for every harness) and no adapter prints it. DOWNSHIFT_QUIET=1 turns it off. See session-models.md.

Spawn state (2026-10-19)

switched / held / observed is computed in telemetry.SpawnStateOf and shown by the shared runner for every harness: one stderr line per spawn, plus live.json for panels. No harness-specific code. Limits: the stderr line only helps where the harness surfaces hook stderr (unverified per harness), and the statusline segment needs a statusline bridge (Claude Code today). Details: spawn-state.md.

Session view (U3, 2026-10-13)

downshift session (tree, --why, --pause) is shared code; what differs is whether a harness gives it a session id. HarnessCapabilities.SessionEnv names the variable a harness exports to commands run from it: Claude Code CLAUDE_CODE_SESSION_ID (seen set in a Bash tool call on Claude Code 2.1.289); others declare none and the command uses the latest session in the log. The hook payload carries a session id for Claude Code and Codex only, so only they group in the tree and can be paused per session. Cursor, Antigravity and KiroCrew events carry none: computed and logged, not groupable, not pausable (the global DOWNSHIFT_NO_ROUTE=1 still applies). The /downshift slash command is Claude Code only. See session-view.md.

Bundled and sibling mods (2026-10-17)

The Claude Code plugin's hooks/hooks.json lists one mod module, hooks/cache-tax/ (third-party, MIT, vendored and pinned; owner decision 2026-10-17). Two more vendored mods ship in the same marketplace as sibling plugins, one install each, because a plugin loads a single hooks module and the three all hook session.start: mods/savvy-progress/ (savvy-progress@downshift) and mods/filetree/ (filetree@downshift); see mods/README.md. None is a routing feature and nothing in the shared layers computes it: a mod is code Claude Code runs in its own process, so it exists only where mods load.

harness mods why
claude-code cache-tax loads with the plugin on 2.1.287+; savvy-progress and filetree are separate plugin installs (CLI, Desktop Code tab, VS Code extension; hooks also run in claude -p, nothing is drawn there) mods are a Claude Code plugin feature; setup cannot write one
codex, cursor, kirocrew, antigravity, grok not available no mod system; the cold-cache question is the harness's own

What each does is in its README; the one fact that matters here is that the cache-tax warming ping spends usage and is armed by the user (or for three hours after a detected cold write), while the guard itself sends nothing.

Answer when nothing is rewritten (2026-10-19)

An allow on an unchanged spawn can override the user's own ask rules, so the shared runner answers neutrally where the host permits it (PR #192) and with the host's required decision where it does not.

Harness Unchanged spawn Why
claude-code, codex neutral {} permissionDecision is optional; updatedInput is only accepted together with allow, so allow is emitted only with a rewrite. Pinned by TestHarnessConformance ("unchanged spawn must emit no permissionDecision").
antigravity {"decision":"allow"} The vendor summary lists decision as required output (allow, deny, ask, force_ask, deny_unless_prior_grant) (vendor-hook-docs). A neutral object would be a missing required field. Not changed.
cursor {"permission":"allow"} The vendor summary documents permission allow/deny and says an invalid response blocks the action; it does not say the field is optional, and no capture of a neutral {} exists. Not changed.
opencode {"v":1,"action":"allow",...} The envelope's action is required by the plugin wire contract.
kirocrew empty stdout, exit 0 exit-code contract.

Whether cursor or antigravity treat an explicit allow as overriding a user prompt rule has not been verified on a live build (no Cursor or Antigravity session was driven). To change either, first capture how the host treats {} for a spawn it has a rule for, then add the harness to the neutral set and extend the conformance decoders. Until then the safe answer is the documented one.

Revalidation

Every TBD cell must be re-checked per harness release: hook contracts evolve upstream and a green cell can regress silently. Failing proof, the tool fails open and the spawn runs unchanged (README.md:755).

A 2026-10-09 sample of Codex spawn_agent inputs recorded key sets only (agent_type, message, task_name, and sometimes fork_turns). It did not include hook stdin, transcript_path, a model field, or executor acknowledgement, so the Codex row above is not refreshed. See closeout-recheck-2026-10-09.md.
