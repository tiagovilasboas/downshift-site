downshift report: routed versus control

Downshift by Tiago Vilas Boas. Updated 19 October 2026. Source on GitHub

On this page

downshift stats estimates savings against a counterfactual baseline. downshift report measures them: a small share of spawns is left unrouted on purpose (the control group), and the report compares what routed and control spawns use per completed task.

downshift report              # last 30 days
downshift report --days=7
downshift report --json       # same numbers, machine-readable

Reading the log is all it does. Nothing is written, and nothing in it is a prompt, a task or a path: counts, rates and token counts. Neither the text nor the JSON report prints a dollar figure.

Tokens per completed task need to see a child end. The report ends with a "Completion measurable, by harness" section: a harness is measurable once it declares an end event and at least one end record (a usage record, or a child_ended that is not a launch) is in the window. Harnesses whose end event is unverified or unknown say so instead of printing zeros. See harness-matrix.md.

The control group

The shared hook runner decides per spawn, for every harness (Claude Code, Cursor, Codex, Antigravity and KiroCrew), by hashing one key per spawn: the correlation id when the harness sends one, else the harness tool-use id, else a fresh id for that call. Claude Code, Cursor and Codex send only a tool-use id, so the settings hook and the mod entry for one spawn, and any retry, land on the same side. The same key always lands on the same side, no state is kept, and the share is accurate to within 1 percentage point. Before 2026-10-19 those three harnesses drew a fresh id per hook call, so the two copies of a spawn routed by both entries could be split between the groups.

Variable Meaning
DOWNSHIFT_CONTROL_SHARE Fraction of spawns left unrouted. Default 0.10. 0 disables the control group. Values are clamped to 0..1; an unparseable value falls back to the default.

A control spawn is classified and logged exactly like any other, but the hook answers with the fail-open response: the spawn runs on the model the harness asked for. The event is recorded with outcome: baseline and the reason code CONTROL. KiroCrew's policy mode never blocks a control spawn.

A control spawn's launch, end and usage link to its decision exactly like a routed spawn's: by the tool-call id, then the agent id (see "Cost linkage" in harness-matrix.md). Logs written before 2026-10-19 have no end record for any control spawn: the linker skipped baseline decisions, so a window that reaches back before that date undercounts the control arm.

DOWNSHIFT_NO_ROUTE=1 and a session pause (downshift session --pause) still win and are unchanged. Their baseline events carry no CONTROL code, so the report counts them as excluded rather than as a control sample: they are not random.

What is compared

For each spawn the report joins the routing decision, the usage record with tokens and how the child ended (the same events stats reads).

  • Routed group: every spawn the router was allowed to decide on, including those it left unchanged. Comparing by intent keeps the result honest: holds and guardrails count.
  • Control group: spawns with the CONTROL code.
  • Completed task: a child that ended completed and has a usage record with tokens. Launched, stopped, unknown and children without tokens are not counted.
  • Rework: a respawn in the same session within 10 minutes after a child ended in error or was interrupted (the same rule as session and stats). The failed child counts as reworked in its own group.
  • Tokens per completed task = the input, output and cache tokens of the same tasks over the number of completed tasks. A failed attempt that a completed task redid is counted with that task. Failed work that never got a successful redo is not added to anyone. It is the A/B check that a cheaper model did not need more tokens. It is a plain ratio, with no interval of its own.
  • Rework rate = reworked spawns divided by spawns with an observed end (completed, error or interrupted).

What the text report prints

The text report shows tokens only. Its table has one row per group:

Column Meaning
spawns Decisions in the group.
ended Spawns with an observed end: completed, error or interrupted.
completed Completed tasks in the group.
tokens/completed Tokens per completed task (see above). - when the group has no completed task.
rework Rework rate.

Once both groups have enough data, one line below the table gives tokens per completed task for routed and control and the change between them, as a point percentage. It is not an interval.

When decisions in the window carry a permission mode, the text report also prints Decisions by permission mode, with a count per recorded label. Claude Code supplies this field; the count is descriptive and does not change routing or the routed-versus-control comparison.

The plan lens follows, labelled Plan lens (tokens only). It is for plans with no per-token bill (Claude Code Pro, Max, Team; Cursor plans), and shows:

  • Tokens saved: tokens that ran on a cheaper model than the one requested in the window. Work (input+output) and cache (read+write) are counted apart, because cache reads carry the smallest price gap.
  • Tokens per completed task, routed against control.

downshift stats and every live view (session tree, panel, statusline, watch) show tokens only.

With fewer than 20 completed tasks in either group the report prints not enough data and no comparison. At a 10% control share that means roughly 200 completed tasks before the first estimate.

The JSON report

--json includes counts and rates, plus token figures: tokens by class (input, output, cache_read, cache_write, total, records) for each group, tokens_per_completed_task, tokens_saved and the completion status per harness. When permission-mode data exists, it also includes the optional decisions_by_permission_mode map. Only built-in Claude Code mode names are stored (default, acceptEdits, bypassPermissions, plan, auto, dontAsk); an unrecognized value is recorded as other, and a missing value is omitted. This count is informational and does not affect routing or comparisons. The report has no dollar key and no interval. downshift stats --export has no dollar key either (schema 3; see stats-export.md).

Limits

  • The report counts tokens and prices none of them. No dollar figure is printed, and no invoice is implied.
  • Tasks differ in size. Random assignment balances that in expectation, but a small window can still be skewed: read the rework rate and the counts, not only the point estimate.
  • A harness that does not report usage or child ends contributes spawns but no completed tasks.
  • Rework needs a session id; spawns without one are never linked.
  • An end without a tool-call id links by session only to an applied rewrite, in both groups, so a control or unchanged routed spawn on such a harness has no end.
  • Before 2026-10-19 a Cursor spawn could also be logged as a claude-code decision (Cursor runs the Claude Code hooks); those copies never end, so they inflate the routed spawn count of older windows. Current versions leave the copy to the cursor hook and record nothing.
  • The control group forgoes the saving by design: about DOWNSHIFT_CONTROL_SHARE of the spawns run on the requested model. Lower it once the sample is large enough, or set it to 0.

See stats-export.md for the counters stats --export adds around this.
